# План тестирования

## 1. Введение

**Цель** — подтвердить, что Kanban-доска соответствует функциональным и нефункциональным требованиям из [requirements.md](requirements.md), и найти дефекты до защиты работы.

**Объект тестирования** — веб-приложение: клиент (React SPA), сервер (REST API и WebSocket на Go), схема базы данных PostgreSQL.

**В объёме:**

- аутентификация и роли;
- проекты, доски, колонки, WIP-лимиты;
- карточки: поля, перемещение, комментарии, вложения, метки, история;
- фильтрация и поиск;
- обновление доски в реальном времени;
- производительность, безопасность, кросс-браузерность, адаптивность.

**Вне объёма:** уведомления и восстановление пароля (не реализуются, поэтому TC-08 из методических указаний неприменим); мобильные приложения; браузеры, кроме Chrome, Firefox и Edge.

## 4. Критерии начала и окончания

**Начало тестирования этапа:**

- функциональность реализована и собирается;
- модульные тесты этапа проходят;
- стенд развёрнут и отвечает на `/readyz`.

**Окончание тестирования:**

- выполнены все тест-кейсы с приоритетом High и Medium;
- нет открытых дефектов с severity Blocker, Critical и Major;
- покрытие кода не ниже 80 % строк и 70 % ветвей на сервере и на клиенте;
- каждый эндпоинт API покрыт интеграционным тестом;
- E2E-сценарии проходят в Chrome, Firefox и Edge;
- под нагрузкой 1000 виртуальных пользователей 95-й перцентиль времени отклика меньше 200 мс, доля ошибок меньше 1 %;
- ZAP не находит уязвимостей уровня High, сканеры зависимостей — уязвимостей High и Critical;
- пайплайн CI проходит полностью.

**Приостановка:** стенд недоступен или дефект блокирует больше половины тест-кейсов этапа.

## 5. Риски

| Риск | Вероятность | Влияние | Меры |
|---|---|---|---|
| Нехватка времени | высокая | не все виды тестирования выполнены | приоритизация тест-кейсов; автотесты пишутся вместе с кодом, а не в конце |
| Нестабильные E2E-тесты | средняя | ложные падения пайплайна | ожидания по состоянию интерфейса вместо пауз, изолированные данные на тест, трассировки для разбора; повторный запуск только в CI |
| Стенд слабее требуемой нагрузки | высокая | порог 200 мс не выдержан из-за железа, а не кода | фиксировать конфигурацию стенда в отчёте; генератор нагрузки запускать с отдельной машины; приводить результаты для нескольких уровней нагрузки |
| Ложные срабатывания ZAP | средняя | время на разбор | файл правил с обоснованием каждого исключения |
| Расхождение клиента и сервера | низкая | ошибки интеграции | типы обеих сторон генерируются из одного файла OpenAPI, CI проверяет актуальность |
| Гонки при одновременном перемещении карточек | средняя | обход WIP-лимита | блокировка строки колонки в транзакции, отдельный интеграционный тест с параллельными запросами |
