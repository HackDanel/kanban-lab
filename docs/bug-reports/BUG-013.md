# BUG-013

**Заголовок:** Под нагрузкой база данных — узкое место: полные сканирования и блокировка строки проекта

**Окружение:** PostgreSQL 17, доска с 10 138 карточками; нагрузочный тест k6 и `EXPLAIN ANALYZE`

**Чем найден:** нагрузочный тест (p95 списка 4,9 с, PostgreSQL занимает более 10 ядер), затем разбор плана запроса

**Шаги:**

1. Засеять доску 10 000 карточек (`setup()` в `tests/load/crud.js`).
2. Выполнить подготовленный запрос списка с фильтром по колонке в режиме `plan_cache_mode = force_generic_plan` (так pgx исполняет повторяющиеся запросы).

**Ожидаемый результат:** Индексный доступ по `(column_id, position)`, чтение около 50 строк.

**Фактический результат:** `Seq Scan on cards … Rows Removed by Filter: 6735` и сортировка всех строк колонки; такой же полный проход для подсчёта. Один запрос с условиями вида `($2 IS NULL OR column_id = $2)` планируется один раз для всех значений параметров, и планировщик выбирает полное сканирование.

Дополнительно: создание и перемещение карточек держали блокировку строки проекта (счётчик номеров) и строки колонки до конца транзакции, и все записи на доске выстраивались в очередь. После включения `pg_stat_statements` это подтвердилось: `UPDATE projects SET card_seq = card_seq + 1` занимал 63 % времени базы (148 мс на вызов), а чтение той же строки по ключу — ещё 16 % (9 мс из-за десятков тысяч мёртвых версий строки). Поиск по тексту сначала находил совпадения во всех досках и лишь затем фильтровал по доске.

**Severity:** Major

**Priority:** High

**Вложение:** вывод `EXPLAIN ANALYZE` (Execution Time 300 мс под нагрузкой), выборки `pg_stat_statements`, замеры `docker stats` в `tests/load/results/`

**Статус:** исправлен:

- запрос списка собирается из заданных фильтров, значения по-прежнему передаются параметрами (`backend/internal/repository/cards_search.go`);
- номер карточки выдаёт последовательность PostgreSQL отдельная для каждого проекта — `nextval` не блокирует строк (миграция `00002`);
- строка колонки блокируется только при наличии WIP-лимита, соседние позиции читаются по индексу вместо всей колонки;
- триграммные индексы включают `board_id` (миграция `00003`), статистика таблицы обновляется чаще (миграция `00004`).

Результат на той же машине: 1773 запроса в секунду вместо 558, p95 по всем запросам 617 мс вместо 3,8 с, ошибок нет.
