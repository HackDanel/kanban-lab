## Нагрузочное тестирование

Сценарии k6 (`tests/load`):

- `crud.js` — до 1000 виртуальных пользователей (разгон 1 минута, 3 минуты под полной нагрузкой) на доске с 10 000 карточек. Каждая итерация: список колонки, поиск по тексту, создание, изменение, перемещение и удаление карточки, затем пауза 1 с.
- `rps.js` — постоянный поток 1000 запросов в секунду в течение 2 минут: страницы колонки со смещением до 3000.

Пороги: p95 < 200 мс, ошибок < 1 %.

Стенд: одна машина (16 потоков, 15 ГБ), на которой одновременно работают k6, Nginx, сервер и PostgreSQL в Docker. Результаты сохранены в `tests/load/results/`.

### Итоговые результаты

| Сценарий | Пропускная способность | p95 | p99 | Ошибки | Результат |
|---|---|---|---|---|---|
| 1000 RPS, чтение | 990 запросов/с, без пропусков | 5,9 мс | — | 0 % | **пройден** |
| 1000 пользователей, CRUD | 2348 запросов/с | 463 мс | 547 мс | 0 % | **не пройден по времени отклика** |

Время отклика CRUD-сценария по операциям, p95: изменение 143 мс, перемещение 186 мс, удаление 201 мс, список 492 мс, создание 485 мс, поиск 527 мс.

### Ход оптимизации

Первый прогон требование не выдержал, и каждое следующее изменение делалось по замерам: журналы Nginx, `docker stats`, `EXPLAIN ANALYZE`, `pg_stat_statements`.

| Прогон | Изменение | Запросов/с | p95, все запросы | Ошибки |
|---|---|---|---|---|
| 1 | исходная версия | 558 | 3772 мс | 31,7 % |
| 2 | keepalive Nginx к бэкенду ([BUG-012](bug-reports/BUG-012.md)); колонка блокируется только при WIP-лимите | 604 | 2615 мс | 0 % |
| 3 | список и поиск собираются из заданных фильтров | 612 | 2667 мс | 0 % |
| 4 | номера карточек из последовательности PostgreSQL вместо счётчика в строке проекта | 1245* | 1054 мс* | 0 % |
| 5 | соседние позиции по индексу вместо всей колонки; триграммные индексы с `board_id` | 1413* | 868 мс* | 0 % |
| 6 | чаще обновляется статистика таблицы карточек | 1773 | 617 мс | 0 % |
| 7 | страница выбирается до вычисления меток и счётчиков ([BUG-015](bug-reports/BUG-015.md)) | 2348 | 463 мс | 0 % |

\* укороченный прогон: 30 секунд разгона и 90 секунд нагрузки.

Главная находка — прогон 4: `pg_stat_statements` показал, что 63 % времени базы занимает `UPDATE projects SET card_seq = card_seq + 1` — все создатели карточек ждали одну строку ([BUG-013](bug-reports/BUG-013.md)).

### Почему порог 200 мс не достигнут

В последнем прогоне PostgreSQL занимает около 12 из 16 потоков машины, сервер на Go — 2, Nginx — 0,25, остальное — сам генератор нагрузки. Отдельный запрос поиска без нагрузки выполняется за 1–1,5 мс, под нагрузкой — около 30 мс: запросы ждут процессор. Сценарий требует от 1000 пользователей около 4300 запросов в секунду с записью на одну доску, и одна машина, генерирующая и обслуживающая эту нагрузку, упирается в процессор.

Что нужно, чтобы выполнить требование:

1. Запускать k6 с отдельной машины, а PostgreSQL — на выделенном сервере (на staging это делает `load.yml`).
2. Не пересчитывать общее число найденных карточек на каждый запрос (кэш в Redis или приблизительный счётчик) — сейчас это самый дорогой запрос.
3. Отдавать чтение доски с реплики PostgreSQL.

## Ограничения

- Staging и production на VPS не развёрнуты: нужны адрес сервера, домены и секреты (см. [deployment.md](deployment.md)). Задачи деплоя в пайплайне написаны и включаются переменной `DEPLOY_ENABLED`.
- Нагрузочные тесты выполнены на одной машине, где одновременно работают генератор нагрузки k6, Nginx, сервер и PostgreSQL; результаты на выделенном сервере будут другими.
- Ручная часть чек-листа юзабилити заполняется при ручном прогоне.
