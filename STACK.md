# Обоснование выбора стека

**Название проекта:** Kanban-доска

**Команда:** Панов Данил Сергеевич, Гостев Данила Сергеевич, группа 9ИС-360

## Выбранный стек

- Frontend: React + TypeScript, Vite, Redux Toolkit (RTK Query), React Router, dnd-kit, Material UI; линтер oxlint, форматирование Prettier
- Backend: Go, chi, pgx + sqlc, goose
- API: OpenAPI 3, генерация кода `oapi-codegen` и `openapi-typescript`, Swagger UI
- БД: PostgreSQL (данные и refresh-токены); Redis для ограничения частоты запросов и рассылки событий между экземплярами сервера
- Real-time: WebSocket
- Тестирование: `go test` + testify, testcontainers-go, gobco, Vitest + React Testing Library + MSW, Postman + Newman, Playwright, k6, OWASP ZAP, govulncheck, gosec, golangci-lint, npm audit, Trivy
- CI/CD: GitHub Actions, образы в GHCR, деплой на VPS по SSH
- Инфраструктура: Docker Compose, Nginx
- Мониторинг: Prometheus + Grafana

## Обоснование

1. **Go на сервере.** Требование — отклик быстрее 200 мс при 1000 одновременных пользователях. Go компилируется в нативный код, каждое соединение обслуживается лёгкой горутиной, а стандартная библиотека уже содержит HTTP-сервер и средства тестирования (`testing`, `httptest`, детектор гонок). Сервер собирается в один статический бинарный файл, образ получается небольшим.
2. **sqlc вместо ORM.** Запросы пишутся на SQL, а sqlc генерирует по ним типизированный код. Все запросы параметризованы, что закрывает SQL-инъекции, и нет скрытых запросов, которые мешают выдержать требование по времени отклика.
3. **Контракт OpenAPI как источник.** Из одного файла генерируются серверные интерфейсы, типы клиента и Swagger UI, поэтому документация не может отстать от кода.
4. **React + Redux Toolkit + dnd-kit + MUI.** Это рекомендованный в методических указаниях набор. RTK Query закрывает кэширование запросов и оптимистичные обновления, нужные для drag-and-drop; dnd-kit поддерживает управление с клавиатуры; MUI даёт адаптивные компоненты.
5. **Playwright.** Один набор тестов запускается в Chromium, Firefox и Edge, есть трассировки для разбора падений в CI.
6. **k6.** Сценарии пишутся на JavaScript, пороги (`p(95) < 200`) проверяются самим инструментом и роняют сборку при нарушении.
7. **GitHub Actions.** Репозиторий размещён на GitHub; для публичных репозиториев сборки бесплатны.

## Рассмотренные альтернативы

- **Node.js + Express + Prisma** (рекомендованный вариант) — отклонён: один поток исполнения и накладные расходы ORM усложняют выполнение требования по времени отклика при 1000 пользователях.
- **NestJS** — отклонён по той же причине; кроме того, больше шаблонного кода.
- **Python + FastAPI** — автоматическая документация OpenAPI, но ниже пропускная способность и два языка в проекте без выигрыша для задачи.
- **GORM** — отклонён в пользу sqlc: неявные запросы и рефлексия во время выполнения.
- **Socket.IO** — отклонён: зрелой серверной реализации для Go нет, а возможностей обычного WebSocket для рассылки событий доски достаточно.
- **Cypress** — отклонён в пользу Playwright из-за более слабой поддержки Firefox и отсутствия запуска в Edge тем же набором.

## Ограничения выбранного стека

- Штатный инструмент покрытия Go считает только покрытие операторов. Покрытие ветвей сервера измеряется отдельным инструментом `gobco`; на клиенте оба показателя даёт Vitest. `gobco` инструментирует один пакет и запускает только тесты из его каталога, поэтому для сервисного и HTTP-слоёв интеграционный набор на время замера копируется в пакет (`backend/scripts/branch-coverage.sh`).
- Генератор типов клиента `openapi-typescript` 7 требует TypeScript 5, а в проекте TypeScript 6; генератор запускается через `npx` отдельно от зависимостей проекта.
- В Go больше явного кода, чем во фреймворках с «магией» (ручная обработка ошибок, отсутствие встроенного внедрения зависимостей), поэтому скорость разработки ниже, чем на Express или FastAPI.
- Клиент и сервер написаны на разных языках, общие типы возможны только через генерацию из OpenAPI.
- Позиция карточки хранится числом с плавающей точкой и требует редкой перенумерации колонки.
